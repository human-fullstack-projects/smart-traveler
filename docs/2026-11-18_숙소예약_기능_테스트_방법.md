# 숙소예약 기능 테스트 방법

마지막 커밋(`39e6d79` "숙소예약 기능 프로토타입 구현")에서 추가된 흐름을 테스트하는 순서다. 이 커밋으로 숙소 검색 → 객실 조회 → 예약 생성(10분 임시 점유) → 토스 테스트 결제 → 예약 확정까지 서버와 연동되도록 바뀌었다. 기존에는 숙소예약 화면이 정적 샘플 데이터였고 서버에 예약을 만드는 API가 없었다.

## 0. 사전 준비 (한 번만)

### 0-1. 테스트 숙소/객실/재고 시드 적재

개발용 DB에 부산 서면·해운대 테스트 숙소와 앞으로 90일치 객실 재고를 넣는다. 이미 실행했다면 다시 실행해도 안전하다(기존 예약 수량은 유지됨).

```powershell
# smarttraveler 폴더에서, DB 접속 정보는 환경에 맞게
mariadb -h 127.0.0.1 -P 3306 -u sixon -p smart_travel_db < src/main/resources/sample-data/busan_booking_seed.sql
```

### 0-2. 토스 테스트 키 설정

`smarttraveler/toss-test.properties` (Git이 무시하는 파일, 없으면 새로 만든다)에 토스 테스트 상점의 주문서형 연동 키를 넣는다.

```text
app.toss.client-key=test_gck_...
app.toss.secret-key=test_gsk_...
```

키가 `test_gck_`로 시작하지 않으면 결제 준비 단계에서 `503 토스 테스트 키를 설정해 주세요.` 오류가 난다.

### 0-3. 로그인 테스트 계정

예약 생성은 로그인한 회원만 가능하다. `docs/시험계정.md`의 여행자 계정을 쓴다.

## 2. 예약 생성까지 테스트

1. 숙소 검색(`#/stays`)에서 지역을 **부산**으로 검색한다. `토요코인호텔 부산서면 (예약 테스트)` 또는 `한화리조트 해운대 (예약 테스트)`가 "1박 평균 최저가"와 함께 나오면 서버 재고 조회(`GET /api/stays?bookable=true`, `GET /api/stays/{id}/rooms`)가 정상 동작하는 것이다.
2. 해당 숙소의 `객실 보기`를 눌러 예약 화면(`#/stays/booking?stay=...`)으로 이동한다.
3. 체크인/체크아웃 날짜와 인원을 바꿔보면서 객실 목록이 다시 조회되는지 확인한다(`loadingRooms` 문구가 잠깐 보였다가 사라짐).
   - 인원을 객실 최대 인원보다 크게 입력 → 해당 조건으로 조회되는 객실이 없어야 한다.
   - 체크아웃을 체크인보다 이전으로 두면 "체크인보다 늦은 체크아웃 날짜를 선택해 주세요." 안내가 나와야 한다.
4. 객실을 선택하고 예약자 이름·연락처·약관 동의 체크박스를 채운 뒤 `예약하고 결제하기`를 누른다.
5. 성공하면 `#/payments/{reservationId}` 로 이동한다. 이때 서버에서 해당 날짜의 객실이 10분간 `HELD` 상태로 잡힌다.

### 확인할 에지 케이스

- **같은 객실·날짜를 두 브라우저(또는 시크릿 창)에서 거의 동시에 예약** → 재고가 남은 수만큼만 성공하고, 초과분은 `409 선택한 날짜에 예약할 수 없습니다.` 로 막혀야 한다.
- **예약 화면을 오래 열어둔 뒤(요금 변경 시뮬레이션 어려우므로 생략 가능) 제출** → 서버 쪽 `expectedTotalPrice` 불일치 시 `409 객실 요금이 변경되었습니다.` 가 나오고 프런트는 객실 목록을 다시 불러온다.
- **비로그인 상태로 예약 화면 진입** → `예약하고 결제하기` 버튼 대신 `로그인하고 예약하기` 링크가 보여야 한다.

## 3. 결제까지 테스트 (토스 테스트 결제)

1. 예약 생성 직후 이동한 결제 화면에서 결제 기한(체크인 10분 전까지)이 표시되는지 확인한다.
2. `토스로 테스트 결제` 버튼으로 토스 위젯을 열고 테스트 결제수단으로 결제를 완료한다.
3. 결제 성공 시 `?stayReservationId=...&stayPaymentResult=success` 쿼리로 돌아온 뒤 `#/payments/{id}/success` 화면으로 치환되고, 서버가 승인 결과를 검증해 `결제 승인 완료 · 예약 확정` 문구가 보여야 한다.
4. `내 예약`(`#/reservations`)에서 방금 만든 예약의 상태가 `CONFIRMED`로 바뀌었는지 확인한다.

### 결제 실패/중단 케이스

- 결제창에서 취소하거나 실패 처리하면 `#/payments/{id}/failure`로 돌아오고 `결제 다시 시도` 링크가 보여야 한다. 이때 예약은 여전히 `PENDING_PAYMENT`이며 점유가 남아있는 동안은 재시도로 같은 주문을 이어서 결제할 수 있다.
- 결제 없이 10분을 넘기면(또는 서버 로그로 `ReservationExpiryJob`이 30초마다 도는 것을 확인) 예약이 자동으로 `CANCELLED`로 바뀌고 점유한 재고(`room_inventory.held_quantity`)가 복구되는지 DB에서 확인한다.

```sql
SELECT reservation_id, status, cancel_reason, cancelled_at FROM room_reservation ORDER BY reservation_id DESC LIMIT 5;
SELECT inventory_id, stay_date, total_quantity, held_quantity, reserved_quantity FROM room_inventory WHERE room_id = <테스트 객실 room_id> ORDER BY stay_date;
```

## 4. API 직접 호출로 확인하고 싶을 때

로그인 세션 쿠키와 CSRF 토큰이 필요하다 (`GET /api/auth/csrf`로 먼저 토큰을 받는다).

| 요청 | 용도 |
|---|---|
| `GET /api/stays?bookable=true` | 서버 재고가 있는 예약 가능 숙소 목록 (로그인 불필요) |
| `GET /api/stays/{lodgingId}/rooms?checkIn=...&checkOut=...&guestCount=...` | 날짜·인원별 예약 가능 객실과 1박 요금 (로그인 불필요) |
| `POST /api/reservations` | 예약 생성, 10분 `HELD` 점유 시작 (로그인 필요) |
| `GET /api/reservations/{id}` | 본인 예약 상세 + 남은 점유 만료 시각(`holdExpiresAt`) |
| `GET /api/reservations/member/{memberId}` | 본인 예약 목록 (본인 `memberId`가 아니면 404) |
