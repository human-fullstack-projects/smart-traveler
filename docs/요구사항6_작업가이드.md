## [2] `/api/stays/search` — 지역(시·도 18개) + 페이지네이션

### 현재 상태
- `StayController.list()`(`smarttraveler/src/main/java/com/smarttraveler/stay/controller/StayController.java:26`)는 `bookable` 파라미터만 받고 지역·페이지 파라미터가 없습니다.
- 지역 선택은 백엔드가 아니라 **프론트에 하드코딩**되어 있습니다. `frontend/src/pages/stays/search/StaySearchPage.jsx:13`의 `regionCenters`에 부산·서울·제주 3개만 있고, `<select>`(197행)도 이 3개만 출력합니다.
- 지역 필터링도 `stay.address.startsWith(applied.region)`(131행) 문자열 매칭으로 처리되어 부정확합니다.
- 반면 `lodging` 테이블에는 이미 `region_id` 외래키가 있고(`Lodging.java:37`), `region` 테이블에는 전국 데이터가 있습니다. 현재 덤프 기준 `region_level='SIDO'` 행이 정확히 **18개**이므로 요구사항의 "시·도 18개"와 일치합니다.
- 비슷한 패턴이 이미 `CourseRegionController`(`smarttraveler/src/main/java/com/smarttraveler/chat/CourseRegionController.java`)에 있어 참고할 수 있습니다.

### 구현 가이드

**1) 시·도 목록 API 추가** (새 엔드포인트, 예: `GET /api/stays/regions`)
```java
@GetMapping("/regions")
public List<RegionOption> regions() {
    return jdbc.query("""
        SELECT region_id, full_name FROM region
        WHERE region_level='SIDO' AND is_supported=TRUE AND abolished_at IS NULL
        ORDER BY region_id
        """, (rs, row) -> new RegionOption(rs.getLong(1), rs.getString(2)));
}
public record RegionOption(long regionId, String fullName) {}
```

**2) 지역+페이지네이션 검색 API 추가** — 기존 `/api/stays`는 그대로 두고 `StayController`에 메서드 추가:
```java
@GetMapping("/search")
public List<StayResponse> search(@RequestParam Long regionId,
                                  @RequestParam(defaultValue = "0") int page) {
    return stayService.searchByRegion(regionId, page * 20, 20);
}
```

`StayRepository`에 region_id 기반 페이지 쿼리 추가:
```java
@Query(value = """
    SELECT l.* FROM lodging l
    WHERE l.status='ACTIVE' AND l.region_id = :regionId
    ORDER BY l.lodging_id
    LIMIT :size OFFSET :offset
    """, nativeQuery = true)
List<Lodging> findByRegion(@Param("regionId") Long regionId, @Param("offset") int offset, @Param("size") int size);
```
> 주의: `lodging.region_id`는 nullable입니다. 기존 데이터 중 `region_id`가 비어 있는 숙소가 있는지 먼저 확인하고, 있다면 주소 기반으로 채우는 보정 작업이 함께 필요합니다.

**3) 프론트 수정** (`StaySearchPage.jsx`)
- `regionCenters` 하드코딩 3개를 제거하고, 마운트 시 `/api/stays/regions`를 호출해 18개 시·도를 `<select>`에 채웁니다.
- 지도 중심 좌표는 `region.center_latitude/longitude`를 쓰면 되지만, 현재 덤프에서 이 컬럼이 전부 NULL입니다(`docs/숙소검색_지도포커스_연동_작업결과.md` 참고). 센터 좌표가 필요하면 시·도 중심값을 별도로 채우는 작업이 선행되어야 하니, 1차로는 지도 중심을 "검색 결과의 좌표 평균"으로 계산하는 방식으로 우회할 수 있습니다.
- 목록 하단에 "더 보기" 버튼을 추가해 `page` 상태를 증가시키고 결과를 이어붙입니다(`liveStays`에 append).

## [3] 빈방·최저가 일괄 조회 API

### 현재 상태
`StaySearchPage.jsx:130~145`에서 목록을 받은 뒤 **숙소 개수만큼 `getRooms`를 개별 호출**(N+1)합니다.
```js
getBookableStays()
  .then((data) => Promise.all(data.filter(...).map(async (stay) => {
    const rooms = await getRooms(stay.lodgingId, applied.checkIn, applied.checkOut, ...);
    ...
  })))
```
숙소가 20곳이면 20번의 `/api/stays/{id}/rooms` 호출이 발생합니다. 외부 OTA나 공공데이터 API 연동은 없고, 전부 자체 `room_inventory` 테이블을 `JdbcTemplate`으로 조회하는 구조(`StayInventoryService.java`)라 백엔드만 수정하면 됩니다.

### 구현 가이드

**1) 일괄 조회 엔드포인트 추가** (`StayController`)
```java
@PostMapping("/availability")
public Map<Long, AvailabilitySummary> availability(@RequestBody AvailabilityRequest req) {
    return inventory.availabilitySummaries(req.lodgingIds(), req.checkIn(), req.checkOut(), req.guestCount());
}
public record AvailabilityRequest(List<Long> lodgingIds, LocalDate checkIn, LocalDate checkOut, int guestCount) {}
```

**2) `StayInventoryService`에 일괄 쿼리 추가** — 기존 `rooms(long lodgingId, ...)`는 그대로 두고, `IN` 절로 한 번에 조회하는 메서드를 추가합니다.
```java
public record AvailabilitySummary(boolean saleable, int minPricePerNight) {}

public Map<Long, AvailabilitySummary> availabilitySummaries(List<Long> lodgingIds, LocalDate checkIn, LocalDate checkOut, int guests) {
    validateDates(checkIn, checkOut);
    var rows = jdbc.query("""
        SELECT r.lodging_id, r.room_id, i.stay_date, i.price, i.is_on_sale,
               i.total_quantity - i.held_quantity - i.reserved_quantity AS remaining
        FROM room r JOIN room_inventory i ON i.room_id = r.room_id
        WHERE r.lodging_id IN (:lodgingIds) AND r.is_active=TRUE AND r.max_capacity >= :guests
          AND i.stay_date >= :checkIn AND i.stay_date < :checkOut
        """, /* ... lodgingId별로 그룹핑 후 available()/total() 로직 재사용해서 최저가 계산 ... */);
    // room별로 묶어 기존 available()/total()과 동일한 기준으로 최저가 산출
}
```
- 기존 `rooms()`의 "모든 숙박일에 재고가 있어야 판매 가능"(`available()`) 로직을 그대로 재사용해 lodging 단위로 묶어서 최저가만 뽑아내면 됩니다.
- `IN` 파라미터가 20개 정도면 네이티브 쿼리 1번으로 충분합니다. JPA `@Query` + `NamedParameterJdbcTemplate`을 쓰면 `List<Long>` 바인딩이 더 편합니다(현재 `JdbcTemplate`은 `IN` 리스트를 직접 바인딩하지 못하니 `NamedParameterJdbcTemplate`으로 교체하거나 `String.join`으로 `?` placeholder를 동적 생성해야 합니다).

**3) 프론트 수정** (`StaySearchPage.jsx`)
- `Promise.all(... map(getRooms))` 블록을 제거하고, 목록을 받은 직후 `lodgingId` 배열로 `/api/stays/availability`를 한 번만 호출하도록 변경합니다.

## [4] 숙소 카드에 사진 넣기

### 현재 상태
- DB에는 이미 `lodging_photo`, `room_photo` 테이블이 있습니다(`LodgingPhoto.java`: `photo_id, lodging_id, image_url, thumbnail_url, sort_order` 등).
- `StayResponse` DTO(`smarttraveler/src/main/java/com/smarttraveler/stay/dto/StayResponse.java`)에는 사진 필드가 없어 API 응답에 사진이 전혀 내려가지 않습니다.
- 프론트 `StayCard`/`StayArtwork`(`StayShell.jsx:26`)는 실제 사진이 아니라 CSS로 그린 가짜 일러스트(산·태양 모양 `<div>`)를 보여주고 있습니다.

### ⚠️ 먼저 확인할 것 — "DB 사진 21,323곳" 수치
저장소 전체(최신 DB 덤프 3종, `data/`, `docs/`, git 커밋 히스토리)를 검색한 결과 "21,323"이라는 숫자는 **어디에도 실제 데이터로 존재하지 않습니다.** grep에 걸리는 건 전부 좌표·해시·TourAPI ID 안에 우연히 포함된 부분 문자열입니다. 확인된 실제 수치는 다음과 같습니다:

| 출처 | 수치 |
|---|---|
| `lodging_photo` 테이블 (덤프 3종 전부 동일) | 143건 |
| `room_photo` 테이블 | 0건 (테이블은 있으나 데이터 없음) |
| `place_image`(관광지 사진, 숙소 아님) | 6,794건 |
| `docs/dummy-data.md`에 적힌 숙소 수 | TourAPI 기준 "숙소 145곳" |
| `smarttraveler/src/main/resources/dummy/lodgings.json` | 145개 숙소, 숙소당 `image_url`/`thumbnail_url` 2개뿐 |

143·6,794·둘의 합(6,937) 모두 21,323과 맞지 않고, 더미데이터 재생성 스크립트(`도구/더미데이터/make_dummy.py`)와 그 응답 캐시는 이 체크아웃에 포함되어 있지 않아(별도 보관 또는 미커밋) 추가 원본 데이터가 있는지도 확인할 수 없습니다. 즉 **이 수치는 요구사항 문서 자체의 오기이거나, 이 저장소에 없는 외부 원본을 가리킬 가능성이 높습니다.** 작업 착수 전 작성자(WBS 담당자)에게 출처를 확인해야 합니다.

API·화면 쪽 구현 자체는 지금 있는 143건(숙소당 최대 2장)만으로도 바로 진행 가능하므로, 수치 확인과 별개로 아래 작업은 착수할 수 있습니다.

## [5] 지도: 보이는 범위만 받기 + 핀 묶기 — 지금은 보류

### 보류 이유
- 지도 마커 로직 자체(`frontend/src/components/map/KakaoMap.jsx`)는 전체 목록을 한 번에 받아 마커를 그리는 구조이고, 뷰포트 필터링·클러스터링은 프론트 로직 추가만으로도 가능합니다.
- 하지만 성능상 의미 있게 동작하려면 `lodging.latitude/longitude`에 공간 인덱스(또는 복합 인덱스)를 추가해야 하는데, 이 테이블은 다른 기능(코스 추천 등)과 공유하는 테이블입니다. 인덱스 추가 자체는 DDL 변경이라 운영 중인 공유 DB에 영향을 줄 수 있어, 문서에도 "위도·경도 색인 추가는 공유 DB 구조 변경이라 팀 동의 먼저"라고 명시되어 있습니다.
- 따라서 **DB 인덱스 변경이 필요한 범위는 팀 합의 전까지 작업 착수 불가**입니다.

### 합의 전 지금 준비해 둘 수 있는 것
- 프론트 전용 변경(인덱스 불필요): 지도 `bounds` 변경 이벤트로 뷰포트 내 좌표만 필터링해서 마커를 그리는 로직, 그리고 마커가 겹칠 때 묶어서 숫자로 표시하는 클러스터링 UI. 이 두 가지는 지금 가진 데이터(최대 146곳)로도 바로 구현/검증 가능합니다.
- 백엔드 쪽은 "어떤 인덱스가 필요한가"(예: `(region_id, latitude, longitude)` 복합 인덱스 vs 별도 공간 인덱스)와 "조회 쿼리 형태"만 설계 문서로 정리해 두고, 팀 합의가 끝나면 바로 DDL을 적용할 수 있도록 준비해 두는 것을 권장합니다.
