# 요구사항3 — 비회원 코스 세션 보관과 로그인 후 이전 작업 전 분석

상태: **2026-11-17 사용자 진행 지시를 받아 구현·검증 완료**. 아래 내용은 작업 전 전달한 설계이며 실제 결과는 `요구사항3_7_8번_작업결과.md`에 기록했다.

요구사항3.txt는 “7,8번 작업은 진행하기 전에 코드 전체 내용을 분석한 후, 어떻게 작업 할 지 자세한 설명을 한 이후에 재진행 여부를 묻는다”고 명시한다. 1~6번 구현과 구분하여 아래 방식으로 제안한다.

## 1. 현재 코드의 전체 처리 흐름

1. `App.jsx`가 `AuthContext`의 회원 상태와 `useAiChat`, `useMyPageStore`를 연결한다.
2. 채팅은 `chatApi.js`에서 CSRF 토큰과 세션 쿠키를 보내 `ChatController`에 접근한다. 서버는 인증 주체별 채팅 토큰으로 대화 접근을 제한한다.
3. `ConditionDialogueService`가 조건을 읽고 `PythonAiClient`를 호출한다. Python `graph.py`는 조건 추출·확인 후 `course_rag.py`로 추천한다.
4. 1~6번 구현에서는 실제 1위 ID를 `recommendedCourseId`로 전달한다. Spring이 후보 포함 여부를 검증하고, **회원의 추천만** `chat_messages.recommendation_json`에 일정 스냅샷으로 기록한다.
5. 화면 표시 후 회원 자동 저장 요청이 호출된다. `RecommendedCourseService.save`가 원본 코스와 별개인 회원 소유 `course`, `course_day`를 만들고 저장된 ID를 같은 추천 메시지에 기록한다. 같은 요청은 기존 ID를 반환한다.
6. `MyPageRepository`는 회원 소유 코스를 조회한다. 방문 시간이 없는 RAG 코스의 방문지는 `condition_meta.itinerary`에서 읽는다. 확인되지 않은 방문 시간을 만들어 `activity`에 넣지 않는다.
7. 기존 비회원 임시 보관은 `mypage/data/store.js`의 React 메모리에 조건과 고정 일정만 저장한다. `pagehide`와 새로고침 때 사라진다. 실제 추천 코스의 서버 세션 보관과는 다르다.
8. 기존 임시 초안의 로그인 후 이전은 `/api/mypage/courses/import`를 사용하며 `mypage_course_draft`로 들어간다. 정식 RAG 코스 저장과 별도 흐름이다.
9. 일반 회원가입은 `SignupService`에서 회원을 생성한다. `SignupPage`는 기존 메모리 코스가 있을 때만 자동 로그인을 시도하고, 그렇지 않으면 로그인 화면으로 안내한다.
10. 일반 로그인은 `AuthSecurityConfig`의 성공 처리, 소셜 로그인은 `SocialSessionLogin`을 거친다. `SocialSessionLogin`은 `changeSessionId()`로 세션 ID를 교체하고 속성을 유지한다. 일반 로그인도 Spring의 세션 고정 공격 방지 처리를 유지해야 한다.
11. `AuthController.me`는 활성·미삭제 회원인지 확인한다. 로그아웃은 서버 세션을 무효화한다. 비회원 데이터는 로그아웃 또는 세션 만료 시 사라지는 정책이 자연스럽다.
12. `GuestChatQuota`와 `guestAiTrial.js`는 존재하지만 현재 주요 채팅 시작 흐름에는 연결돼 있지 않다. 요구사항3에 없는 새로운 비회원 횟수 제한을 이 작업에서 추가하지 않는다.

## 2. 제안하는 7번 구현

- 비회원도 현재와 같이 추천 결과를 먼저 표시한다. 저장 대상은 확정된 기준대로 **1위 코스 1개**다.
- 회원과 같은 서버 검증으로 추천 메시지에 일정 스냅샷을 기록하되, 아직 회원 소유 `course`는 생성하지 않는다.
- 화면 표시 후 비회원 보관 API를 호출한다. 서버가 요청의 채팅·메시지 소유권을 검사하고 추천 스냅샷을 **Spring `HttpSession`** 속성에 보관한다.
- 보관 내용은 추천 메시지 ID, 원본 코스 ID, 코스명, 목적지, 요청 날짜·인원·동행·교통수단, 일차별 장소 ID·이름·순서다. 브라우저가 전송한 코스 내용이나 회원 ID는 신뢰하지 않는다.
- 서버 세션에 보관하므로 새로고침과 사이트 내부 이동으로 사라지지 않는다. 세션 만료·로그아웃·서버 세션 소실 시에는 사라진다.
- 세션에는 보관 상태 조회 기능을 추가하여, 새로고침 후에도 보관 여부와 로그인 안내를 확인할 수 있게 한다.
- 여러 번 새 추천을 받으면 세션에 보관할 대상은 **마지막으로 표시한 추천의 1위 코스 1개**로 갱신하는 방식을 제안한다. 회원에게 이전된 결과는 추천 메시지별로 중복 생성하지 않는다.

## 3. 제안하는 8번 구현

1. 회원가입만 완료한 시점에는 저장하지 않는다. 로그인 성공 후 활성 회원 확인이 끝나면 세션 코스 이전 API를 호출한다.
2. 일반 로그인·소셜 로그인·이미 로그인된 상태의 새로고침에서 같은 이전 API를 사용한다. 로그인 방식별로 서로 다른 저장 로직을 만들지 않는다.
3. 서버는 `HttpSession`의 보관 코스와 **현재 서버 인증의 회원 ID**를 사용한다. 요청 본문에서 회원 ID·코스 소유자를 받지 않는다.
4. 이전을 처음 시도한 회원에게 보관 정보를 연결한다. 실패 후 다른 계정으로 바뀌었을 때 그 계정으로 임의 이전하지 않는다.
5. 트랜잭션에서 회원 코스와 일차별 날짜를 저장하고, 기존 추천 메시지에 결과 코스 ID를 기록한다. 이미 저장된 추천이면 그 ID를 반환한다.
6. **DB 커밋 성공 이후에만** 세션의 보관 데이터를 지운다. 실패하면 데이터를 유지하고 다시 이전할 수 있도록 한다.
7. 저장 후 `my-courses`를 갱신한다. 자동 이전을 위해 이전 계정의 채팅 기록 접근 권한을 복원하지 않는다.

가입·로그인 사이의 화면 이동과 세션 ID 교체에서 보관 속성을 유지하는 것이 핵심이다. 기존 React 메모리 초안 이전과 새 서버 세션 RAG 이전을 구분하여 같은 코스가 두 테이블에 중복 저장되지 않도록 한다.

## 4. 필수 검증

- 비회원 추천 표시 후 세션 보관, 새로고침 후 보관 유지.
- 회원가입 후 로그인 및 기존 회원 로그인 후 정확한 회원에게 코스 이전.
- 같은 이전 요청 반복·여러 탭 동시 요청에서 코스 1개만 생성.
- DB 저장 실패 시 보관 정보 유지, 다시 시도하면 정상 저장.
- 계정 전환 시 다른 회원에게 잘못 이전되지 않음.
- 세션 만료·로그아웃 후 남은 정보가 노출되지 않음.
- 회원 직접 추천 자동 저장과 기존 개인화 추천·마이페이지 회귀 통과.

위 설명 이후 사용자가 **“진행해라”**고 지시하여 7·8번 구현과 검증을 진행했다.
